# Consensus Radar

A Wavelength-style calibration game for teams. One player sees a hidden spot on a dial and describes it with a clue; their teammates each place their own marker on their own phone, and the server averages those markers into the team's answer. Everyone else bets on which side of the secret the team will land.

The original prototype was a single HTML file. This repository is the deployable version of it: a Next.js app with a real backend, persistent rooms, and a leaderboard. The prototype is kept at `legacy/consensus-radar.html` as an offline single-file fallback — it still works by double-clicking, needs no server, and shares no code with the app.

## What you need

- Node 18.18 or newer
- A free Supabase project (Postgres + Realtime)
- A Vercel account for hosting (optional for local play)

## Setting up Supabase

Create a project at supabase.com, then open the SQL editor and run two files, in this order.

`supabase/schema.sql` first. It creates the room and round tables, the isolated secret tables, the durable stats tables, the scale catalogue table, the analytics events table, the leaderboard and analytics views, the row-level-security policies, the Realtime publication, and the two housekeeping functions the nightly cron calls. The script is idempotent — `create table if not exists` for tables and an explicit `alter table ... add column if not exists` block for columns added after the first release — so running it again on a project that already has data is safe and is how you pick up schema changes.

`supabase/scales-seed.sql` second. It fills the `scales` table with the 262 bilingual pairs. It upserts on the key, so re-running it is safe too, with one caveat: it resets the labels of any pair you edited in the dashboard back to the wording in the repository.

Both files run as a single transaction, which is worth knowing when one fails: the Supabase SQL editor wraps a whole script in `begin`/`commit`, so a single failing statement rolls back everything above it. An error like `42P01: relation "public.scales" does not exist` while running the seed therefore means `schema.sql` did not complete, not that the seed is wrong. Fix `schema.sql`, run it until it reports success, and then run the seed. `GET /api/health` names any table or column that is still missing, so it is the fastest way to check the database matches the code.

Then copy `.env.example` to `.env.local` and fill in the three values from Settings → API:

```
NEXT_PUBLIC_SUPABASE_URL=https://<project-ref>.supabase.co
NEXT_PUBLIC_SUPABASE_ANON_KEY=<anon public key>
SUPABASE_SERVICE_ROLE_KEY=<service_role secret key>
```

Five more variables are optional. `ANALYTICS_TOKEN` locks the analytics API behind a shared secret and `NEXT_PUBLIC_TRACK_POINTER=1` turns on the sampled pointer heat grid; `MIXPANEL_TOKEN` and `MIXPANEL_HOST` mirror events to Mixpanel. Those four are described under Analytics below. `CRON_SECRET` switches on the nightly housekeeping job and is described under Deploying.

The service-role key must never get a `NEXT_PUBLIC_` prefix. It is used only inside API route handlers, where it never reaches the browser. The anon key is public by design and is used for one thing only: opening the Realtime websocket.

## Running locally

```
npm install
npm run dev
```

Open http://localhost:3000, create a room, and join the same room code from a phone on the same network (use your machine's LAN address) to see the own-device flow properly.

`npm run verify` runs the full gate: `tsc --noEmit`, the unit tests, and a production build. Run it before every deploy.

## Deploying to Vercel

Import the repository in Vercel; the framework is detected automatically and no build settings need changing. Add the same three environment variables under Settings → Environment Variables for Production, Preview, and Development, then deploy. `GET /api/health` is a cheap liveness check that confirms the app can reach Supabase; it also reports which scale catalogue is live, so `"scales":"builtin"` is the sign that the seed file never got run.

The app pins Node 22 through `engines` in `package.json`, which is the version it is tested and built against. Vercel warns when its project setting disagrees and then honours `engines` anyway, so the warning is cosmetic; setting Settings → General → Node.js Version to 22.x silences it.

Rooms are ephemeral, so nothing needs migrating between deploys. Nothing in the game expires on its own, though — a room lives until something deletes it — so `vercel.json` schedules one daily job at 04:00 UTC against `GET /api/cron/cleanup`, which drops rooms untouched for more than 48 hours and analytics events older than 90 days. Finished games are copied into the durable stats tables the moment the winner screen appears, so the leaderboard never depends on a room still existing and the purge cannot cost a result.

That route is gated on `CRON_SECRET`, which Vercel sends as `Authorization: Bearer <secret>` on every cron invocation of a project that has the variable set. The gate is not decoration: the handler holds the service-role key, so an open URL there would be an unauthenticated delete button. **A missing variable means the route refuses everything with a 503** — closed by default, so a deploy that forgets the secret loses the cleanup rather than exposing it. Both deletions are `security definer` functions in `supabase/schema.sql` with `execute` revoked from `anon` and `authenticated`, which is why the route is a dozen lines: the rules about what may be deleted stay next to the tables they delete from, and this stays a trigger. They are also called independently and reported separately, so an un-migrated database missing one function still gets the benefit of the other.

## How the game works

The host creates a room, picks the team names, the scale categories (general or analytics), the target score, whether side bets are on, and how long each half of a round may take (see Clocks). Players join with the four-character room code and pick a team. At least two teams need **two** players each before the game can start, and nobody may be left alone in a team — the clue-giver doesn't place a marker, so a team of one has a clue and nobody to answer it, which is a round that cannot resolve. The lobby names the teams that are short, shows the shortfall next to each team in the picker, and keeps Start disabled until the room is playable; `startGame` enforces the same rule server-side for a stale client or a direct API call. Mid-game the rotation skips a team that has shrunk below two, falling back to any non-empty team only if nothing else is playable — a stalled round the host can reveal beats a room that cannot advance at all. `MIN_TEAM_SIZE` in `src/lib/game/engine.ts` is the single place the number lives.

Each round picks a scale that hasn't been used yet in that room and a secret target between 5 and 95. The catalogue holds 262 pairs — about 180 general and 82 analytics — so a long evening never repeats itself. The clue-giver on the active team is whoever has given the fewest clues so far, ties broken by join order. They see the target; nobody else does. They write a clue under the rules below. Their teammates then each drag their own slider and lock it in, without seeing each other's. The other teams see the clue and watch the markers appear on the dial — each as a faint needle, and their running mean as one bright needle with a disc on it, because the mean is the only position the round is ever scored on and five equally faint needles is a picture with no answer in it. That highlighted average is what their left-or-right side bet is a judgement about. Once everyone who can act has acted the round reveals automatically, and the round's clue-giver can force the reveal early.

## Whose buttons these are

Reveal, Skip and Next belong to the round's clue-giver and to nobody else. A round belongs to one person at a time: the clue-giver is the only player who knows whether the table has finished talking, and the only one for whom revealing early costs something. When the host held the same buttons, four other people watched a round end for reasons they were not part of — and the host is very often on another team, which made it somebody else's turn being ended. The rotation is what makes this fair rather than a privilege, since a different person gives the clue every round.

`mayControlRound` is the one predicate behind all three buttons, and the client draws them with the same function the server enforces with, so a button is only ever offered to somebody it will work for. Everyone else gets a waiting line rather than a disabled control — a button you can see but never press is a worse explanation than no button.

## When a room stops moving

Every button in the paragraph above belongs to somebody, which is fine until that somebody closes their tab. Two failures follow from it, and both used to end the evening rather than the round.

**A round nobody can finish.** Until a clue exists, the guessers have no control at all — no slider, no lock, nothing to press. If the clue-giver walks away, or looks at the pair and has nothing to say about it, the room sits on an empty dial indefinitely. `skipRound` is the way out: the round is deleted rather than scored, the scale goes back in the undealt pool, `round_no` rolls back so the retry reads as a second attempt at the same round, and the turn passes to the next team that actually has enough players. Deleting rather than marking it skipped is what keeps a rescued round out of `game_results.rounds_played`, out of `v_scale_stats`, and out of everybody's average — an abandoned round is not a data point about a scale or a player.

Who may press it follows the rule above: the round's clue-giver, right up to the reveal. Plus — and this is the clause that actually unsticks the dead end — **anybody in the room once the clue-giver has been quiet for two minutes**, because the people staring at an empty dial are usually not the person who left. Not the host specifically, who may well *be* the person who left. A clue-giver id that is null, or one with no matching player, counts as away for the same reason: the seat the round is waiting on is empty.

Skipping stays available in the guess phase too, not just the clue phase. Markers are already down by then, but a clue nobody can read is worth zero and a forced reveal can cost the team two points for guessing on the wrong side of the dial — so giving up is the kinder of the two exits, and the clue-giver is the one who can tell which situation they are in. Once a round is revealed there is nothing left to rescue; `next` is the way on.

**A room with no host.** Starting, settings, ending the game and play-again are host-only, so a host who closed their tab leaves everyone else looking at a room that cannot move. After two minutes of silence the crown is offered to whoever is still there, as a button rather than an automatic promotion: the server cannot tell a host who left from one who is reading the scale out loud, and the people in the room can. The claim is atomic — a conditional update on `rooms.host_player_id` — so two people pressing at once produces one host, not two. A leave is handled separately and immediately: `leaveRoom` picks a successor before the row is gone, and then re-runs the auto-reveal check, because the player who just left may have been the last one the round was waiting on.

Both of these depend on knowing that somebody has gone quiet, and that turned out to be the load-bearing part. `players.last_seen_at` moves only on *authenticated* requests, and reading the room state carries no credentials — so an idle host makes no authenticated requests at all and would read as absent after two minutes in every ordinary room. The host and the current clue-giver therefore send a deliberate heartbeat every 45 seconds while their tab is visible. Only those two, and only visible: writing to a table Realtime watches on a read path would make every heartbeat a refetch for everybody, which is a loop rather than a heartbeat. A backgrounded phone stops beating on purpose — a host in somebody's pocket genuinely is away.

`AWAY_AFTER_MS` in `src/lib/game/engine.ts` is the single place two minutes lives, and `hostIsAway`, `clueGiverIsAway`, `pickNewHost`, `canSkipRound` and `mayControlRound` are pure functions with no I/O, which is why they are the part under test. Both hatches are instrumented as `round_skipped` and `host_claimed` — see Analytics, where they are treated as failure signals rather than features.

## Clocks

The rescue hatches above are for a room that has already stalled. The clocks are for the far more ordinary case: one person is thinking, and four are waiting on them with nothing to press.

The host chooses two limits in the lobby, from unlimited, 1, 3 or 5 minutes, and they are fixed for the game. Two and not one, because the two jobs are nothing alike — writing a clue is a blank page, and moving a slider you are already looking at is a decision, so a single limit is either cruel to the clue-giver or no limit at all for the guessers. **Both default to unlimited**, which is exactly how every room played before this existed; a host who ignores the setting sees no countdown anywhere.

What happens at zero is different for each phase, because what is lost is different. **A guesser who runs out is credited with 50** — dead centre, which is both the dial's default position and what somebody who never touched it was looking at. It is a real marker, not a forfeit: it can score a bullseye if the secret is near the middle, and that is correct rather than generous, since the round is an average of a team and not a punishment for one slow phone. Filling it in is the kind option too — a team of three whose third member goes quiet gets one ordinary marker at the centre instead of having its mean dragged into a corner. **A clue-giver who runs out costs their team the round**: it is revealed with no clue, no marker and zero points, the secret is shown, and the turn passes on the ordinary Next press so the table sees why nothing was scored. Revealed rather than deleted, which is the one place this differs from `skipRound` — the round number stands, it counts in `rounds_played`, and a clue-giver who repeatedly says nothing is visible in the history rather than erased from it. No `player_round_stats` rows are written for such a round: nobody aimed at anything, so a row would only drag an average around with a number that describes no attempt.

The mechanism turns on one decision. A phase stores the **instant it ends** — `rounds.phase_deadline`, written by the server — and never a remaining duration. Five phones counting their own seconds drift and expire at five different moments; five phones counting down to the same instant agree. It also means a tab that slept through the whole phase wakes up already knowing it is over, with nothing to reconstruct. `RoomState.now` carries the server's clock on every read so each client can measure its own offset, and that offset is deliberately taken against the response's *arrival* rather than its issue: it reads the server as very slightly earlier than it is, so the countdown runs a fraction long. Long is the safe direction, because the server refuses anything early and a late client is corrected by waiting. The guess clock is restamped when the clue lands rather than inherited from the round's birth — the guessers could not have begun before the clue existed.

Expiring is client-initiated, by **any** device, through `POST /api/rooms/:code/actions/expire`. The alternatives are worse: a lazy write inside `getState` would make every read a Realtime event and every Realtime event a read, and a server-side timer would mean a cron waking every few seconds for games nobody is playing. Restricting the call to the host or to the player on the clock puts the escape route in the hands of exactly the person most likely to have walked away. So whichever tab notices first asks, the server claims the phase with a conditional update — `.eq("phase", …).eq("phase_deadline", …)` — and the other four asking in the same second are handed the same fresh state rather than an error. The server re-checks the deadline against its own clock and is the real guard; `EXPIRE_GRACE_MS` (1.5 s) only stops a fast phone making a request that would be refused.

On screen the countdown turns amber at 20 seconds and red for the last five, and the phone beeps and vibrates — but **only on the device that still owes an action**. A beep on every phone in the room turns a warning into a stampede, and the people who have already moved can do nothing about it. The tones are synthesised with two oscillators in `src/lib/client/alarm.ts` rather than played from a file, because an audio asset is a network request that fails exactly when it matters; every part of it is best-effort and silent where it cannot work, since the amber and red are the real warning. `prefers-reduced-motion` drops the pulse and the bar's transition.

`TIMER_CHOICES`, `AUTO_MARKER`, `TIMER_WARN_AT`, `TIMER_FINAL_AT`, `EXPIRE_GRACE_MS` and the pure functions around them — `cleanTimerSeconds`, `phaseSeconds`, `deadlineFor`, `secondsLeft`, `timerLevel`, `mayExpire`, `formatClock` — all live in `src/lib/game/engine.ts` and take `now` as an argument, which is what makes every boundary testable. `timer_expired` carries `round` and `phase`; see Analytics. One last property worth knowing: on a database where `schema.sql` has not been re-run, the three new columns are simply absent, every limit reads as unlimited, and no UPDATE ever names `phase_deadline` — the feature disappears rather than breaking the room.

## Teaching the game without a video

`/how-to-play` explains the game by playing it. A drawn cursor moves across a phone-sized frame, types a name and a room code, joins, changes team, writes a clue and gets it rejected for containing a number, rewrites it, drags a slider, locks a marker, places a side bet and reaches the reveal — narrated a sentence at a time in whichever language the header is set to. Nothing is real: no room is created, no request is made, and the only event the page sends is `howto_open`.

The build is three files. `src/lib/demo/script.ts` is the whole performance as data — a cast, one round's numbers, and a list of steps (`type`, `click`, `drag`, `say`, `screen`). `src/components/demo/DemoScreens.tsx` renders the screens. `src/components/demo/DemoPlayer.tsx` walks the list: a sequential async loop where every step awaits its own duration, so inserting a sentence never re-times what follows, and the cursor is measured with `getBoundingClientRect` against the stage on each step rather than scripted in pixels, so it stays on target through a reflow, a font change or a narrow phone.

Two decisions are worth knowing. The screens are mock-ups rather than the real `PlayView` and `HomePage`, because those need a live room state, an identity and a `run` that talks to the API — faking all three to drive an animation would be a second implementation of the game with none of its safety, and it would fire tracking events into the real funnel. What keeps the mock honest is that every class in it is the app's own global CSS class, so a visual change to the product changes the tutorial too, and the pure logic is the real thing: `Gauge` draws the dial, `validateClue` rejects the bad clue, and `scoreFor` decides the three points shown at the reveal. And the narration is stored as dictionary keys rather than sentences, so the caption bar follows the UA/EN toggle like the rest of the app; switching language restarts the run, which is honest, because the clue being typed is different text.

The frame is `aria-hidden` and `pointer-events: none` — it is a performance, not a control surface — autoplay is suppressed under `prefers-reduced-motion`, pausing takes effect between steps rather than mid-word, and the same rules are repeated in prose underneath for anyone who is not watching an animation.

## What a clue may say

A clue has no numbers in it and is at most six words long. Both rules live in `validateClue` in `src/lib/game/clue.ts`, which is pure and is called from two places: the input box, on every keystroke, and `submitClue` on the server. One function, so the form cannot be more permissive than the server and — the failure that actually teaches players to distrust a form — cannot be stricter either. The word lists sit apart in `src/lib/game/clue-words.ts` so they can be edited without reading the algorithm. Rejections are returned as reason codes rather than sentences, and `src/lib/i18n.ts` turns each one into a message that says what to change, in Ukrainian and English.

"No numbers" is three checks. Digits anywhere in the string, tested with `\p{N}` rather than `\d` so it also catches fractions like ½ and the Unicode Roman numerals Ⅰ Ⅴ Ⅹ, which sit in the wider number categories. Numbers spelled out, matched against a closed list — English does not inflect so exact words carry it, while Ukrainian needs stems, because "п'ять" also appears as п'яти, п'ятьох, п'ятьма and п'ятий. And numbers hiding inside a glued token, so `halfthewaydown` is reported as a number rather than as a mess.

Two collisions are handled deliberately rather than left to chance, because a false rejection costs more than a miss. "другий" is a number but "друг" is a friend, so only the unambiguous inflections of *second* are listed. "п'ятниця" is Friday, not a five, so it is exempt from the "п'ят" stem. ASCII Roman numerals are knowingly not enforced at all: `MIX`, `CD`, `XL` and `VI` are valid Roman numerals and also real words, and `I` is a pronoun.

The six-word cap counts words that carry meaning. Articles, prepositions and the plain conjunctions are free, on the grounds that charging a player one of their six for "the" only teaches them to write telegrams. A second, looser cap on the total token count stops the free list being used as padding.

Stopping words being glued together to beat the cap is the only rule that needs a heuristic, so it is layered to make the heuristic do as little as possible. First, a separator is defined as anything that is not a letter, a number, a combining mark or an apostrophe — which makes `so-like-this-word`, `so.like.this.word` and `so_like_this_word` four words each, with no guessing at all, and covers every easy evasion in one rule instead of one rule per character. Zero-width characters are stripped rather than split on, because they are invisible to the guessers and the count should match what is on screen. What remains is true concatenation, `solikethisword`, and a length cap cannot separate that from a real word: it is 14 characters while `відповідальність` is 16 and `непередбачуваність` is 18. Neither can syllable counting, since glued words are made of real words. So any token of twelve characters or more is segmented against a compact list of common short words and rejected only if the *whole* token decomposes into three or more of them, at least two of real-word length. `solikethisword` becomes so + like + this + word and is rejected; `responsibility`, `characteristic`, `відповідальність` and `непередбачуваність` do not decompose at all and pass. The handful of real words that do decompose — `nevertheless`, `understanding` — are named in an exemption list.

The failure direction is chosen, not accidental: a token nobody can segment is allowed through. Someone determined to defeat the heuristic is cheating in front of their own team, and the host can already force the reveal and move on. Whether the rules are calibrated is a measurable question rather than a matter of opinion — `clue_sent` carries a `blocked` property naming the first rule that got in the way, absent when the clue went out first try, so a rule that mostly annoys people shows up as a dominant reason in Mixpanel. See `ANALYTICS.md`.

Scoring is the prototype's, with one rule tightened. The team's marker is the mean of the submitted guesses. Within 5 points of the target is a bullseye worth 5, within 12 is 3, within 40 is 0, and further than that is −2. Play continues until a team reaches the target score, or forever in endless mode.

The side bet needs the whole team, not a majority. Each watching team gets +1 only if **every** bet it placed called the same side, and that side was right; a split pays nothing at all. Under the old majority rule two people could tap opposite sides and still collect, which made the bet free — you could not lose it, so there was nothing to discuss and nothing to get wrong. Requiring one voice restores the only interesting part, which is that the team has to agree out loud before anybody taps. Abstaining is silence rather than opposition: only bets actually placed are counted, so two people who agree are not punished for a third who never voted — the same treatment the auto-marker gives a guesser who never moved their slider. While the round is live each phone shows its own team's votes as chips and warns, in red, when the team is currently split. `teamBetPoints` and `betConsensus` in `src/lib/game/engine.ts` are the two pure functions behind that, one for the score and one for the screen.

## How the secret stays secret

Going own-device means the target has to survive being on the same page as the players who mustn't see it. Three things make that work.

The hidden values live in their own tables — `round_secrets`, `guess_values`, `player_tokens` — which have row-level security enabled and no policies at all. That combination makes them unreachable by the anon and authenticated roles; only the service role, which exists solely inside the API routes, can read them. The clue-giver gets the target through `GET /api/rooms/:code/secret`, which checks server-side that the requester really is this round's clue-giver.

The public `guesses` and `bets` rows carry only who has acted, never what they chose, so the Realtime payloads are safe to broadcast. Bet sides are folded into the round's `reveal_detail` at reveal time and only then become visible; slider values are handled by their own rule, below.

## Who sees what

Secrecy in this game is per-role, not per-phase, so it is worth stating in one place. The secret target is the clue-giver's alone until the reveal. The clue itself is public from the moment it is sent — every player in the room sees the same text, on the same screen, for the rest of the round; that is the point of it. Individual markers split three ways: a guesser sees only their own, the watching teams see all of the active team's as they arrive, and everybody sees everybody's at the reveal.

That middle case is the one that needs an argument. The watching teams have to bet which side of the marker the secret sits on, and in the board game they can see exactly where the dial was left before they call it — hiding the markers made that bet a coin flip rather than a judgement. The active team is the opposite case: the score comes from the mean of their markers, so a guesser who could see their teammates' would anchor on them, and the round would measure agreement instead of calibration. The clue-giver is treated as part of the active team here and sees nothing either.

Because that is a rule about the viewer rather than about the round, it cannot live in the room state — `GET /api/rooms/:code` builds one payload and hands the same one to everybody. So the markers get their own authenticated endpoint, `GET /api/rooms/:code/watch`, modelled on the secret-target one: it checks server-side that the caller is not on the guessing team and reads `guess_values`, which `getState` never touches. The client fetches it only when it is entitled to, refetching whenever the guess set changes — including a re-submit, which leaves the row count alone and only moves `submitted_at`. A guess row is written before its value is, so a fetch that lands between the two would see a guesser with no marker; the server drops such a row rather than drawing it at zero, and the client asks again, twice at most so a genuinely missing value cannot become a polling loop. Watchers see the markers as faint needles on the dial and as numbers next to the names in the progress list.

Realtime itself is treated as a doorbell rather than a data source. A change on any watched table triggers a debounced refetch of `GET /api/rooms/:code`, which recomputes what each requester is allowed to see. The client never derives state from a websocket payload, so there is exactly one authoritative version of the game and no way for a client to drift or spoof its way forward. Polling backs this up at 2.5-second intervals when the websocket is down and 15 seconds when it is up, plus an immediate refetch when a tab regains focus.

## The scale catalogue

The 262 pairs are authored once, in TypeScript, and used three ways. `src/lib/scales-data.ts` is the single source: 180 general pairs grouped by theme and 82 analytics ones, each a `[key, uaLeft, uaRight, enLeft, enRight]` tuple. `npm run scales:sql` regenerates `supabase/scales-seed.sql` from that file, so the SQL is never hand-edited and cannot drift. At runtime `src/lib/server/scales.ts` reads the enabled rows out of Postgres, caches them for five minutes, and falls back to the TypeScript list if the table is empty or the query fails — a missing seed makes the game blander, not broken.

Living in the database is what makes the catalogue editable without a deploy: adding a pair in the Table Editor puts it in play within five minutes, and setting `enabled = false` retires one without touching the stats it already produced. Round rows store the exact wording they were dealt, in both languages, so rewording or retiring a pair never rewrites history.

Keeping 262 pairs out of the browser bundle took a little care. `src/lib/scales.ts` holds only types and pure helpers, `pickScale` takes a pool rather than reaching for the catalogue itself, and the client reads pole labels off the round row through `storedLabels`. The catalogue is therefore server-only — the production build has no scale text in `static/`, only in the server chunks — and the client needs no dictionary at all.

## Identity without accounts

There is no sign-in, and there are two separate ideas of "who you are".

Joining a room mints a `{playerId, token}` pair. The token is stored in localStorage and sent as `x-player-id` and `x-player-token` headers on every action, where it is checked against `player_tokens`. This is the credential: it authorises moves, and it belongs to one room.

Alongside it, each browser mints a `cr:player-uid` once — 32 random hex characters — and keeps it for every future game. It is not a credential and grants no access to anything, so leaking it does nothing; its only job is to make "Dmytro" one row on the leaderboard instead of one row per game. It travels with room creation and joining, is stored on `players`, and is copied onto every `player_round_stats` row at reveal time.

The trade-offs are worth stating plainly. A different browser, a private window, or cleared site data is a different player. Anyone who plays on this browser plays as this id. And two different people who share a name on two devices stay two rows — telling them apart needs a real account, which is exactly what this game is designed not to require.

Two rows with the same label is still a readability problem, so each leaderboard row carries a four-character tag derived from its device id, shown when a name is claimed by more than one row: `Dmytro · K7QM` and `Dmytro · R3BX` are visibly two people. The tag is a salted FNV-1a hash rather than a slice of the id, which matters for two reasons — a prefix would publish the actual id to every browser that opens the leaderboard, and a hash is cheap enough to compute identically on both sides. That last property is what lets the page highlight your own row: the browser hashes its *own* device id and looks for a match, so the server never learns which row belongs to whoever is looking. `src/lib/player-tag.ts` is the whole of it. Four characters over a 32-symbol alphabet is about a million possibilities, which is not collision-proof and doesn't need to be — it only has to separate the handful of people in one office who picked the same first name.

Games played before the id existed still count. `player_round_stats` rows with no id group by lower-cased name, and a name-only group is folded into the device group that answers to the same name, so a returning player is not listed twice. The SQL view `v_player_stats` mirrors the simpler half of that rule — `group by coalesce(player_uid, lower(player_name))` — for ad-hoc queries in the SQL editor; the API does the fold.

That fold is also the honest limit of all this. A browser that cannot keep storage has no id, so typing somebody else's name lands in their row — which is what the leaderboard did for everybody before, and is the price of keeping the old scores. The ids themselves never reach another player's browser (room state blanks them out), but they aren't a security boundary and nothing here would survive somebody who actively wanted to game it. For a party game among colleagues that seemed like the right place to stop; a real fix is accounts, which is the one thing this game refuses to ask for.

The device id earns its keep a second way: it makes joining a room idempotent. One device gets one seat, so a second `POST /api/rooms/:code/join` from the same browser hands back the seat it already owns with a fresh token rather than inserting another player. Their name and their team survive, because the rest of the table already knows them by both. `supabase/dedupe-players.sql` adds a partial unique index on `(room_id, player_uid)` that enforces this in the database as well, since the application is not the last word on it.

That matters more than it sounds. Retrying a join is completely normal — the network eats the answer, a tab loses its storage, somebody just reloads — and until this was idempotent every retry created a real new player. One phone that kept landing back on the join screen put eleven copies of the same person in one lobby, each named a little more absurdly than the last: `Anton 3`, `Anton 3 2`, `Anton 3 2 2`. The suffix is `uniqueName()` doing exactly what it was told.

## Reading the room state, and one iOS trap

The client treats Supabase Realtime as a doorbell rather than a data feed: any change to the room's tables triggers a debounced refetch of `GET /api/rooms/:code`, which is the single authoritative answer. A poll runs underneath as a safety net — every 2.5 s while the websocket is down, every 15 s once it is up — plus a refetch whenever the tab becomes visible, because phones sleep aggressively.

All of which is useless if the phone answers the fetch out of its own cache, and this is a real thing mobile Safari does. Every read is therefore given a URL nothing has seen before (`?_=<timestamp><counter>`, see `cacheBust` in `src/lib/client/api.ts`) on top of the `no-store` on both the request and the response. A URL that is new cannot be in any cache — not Safari's, not a proxy's, not a CDN's.

This was not theoretical. Because the room state is a plain GET, a phone could hold the response captured the instant the room was created — one player, the host — and re-serve it to every poll forever. The player never appeared in their own room, so the join screen came back, so they joined again, and the room filled up with ghosts. The tell was that `GET /api/rooms/:code/me` stayed correct throughout: it carries the identity headers, so it was never a cache candidate. When the server insists you are in a room whose state does not list you, suspect the transport, not the database.

## Analytics

The leaderboard answers "who plays well". Analytics answers a different question: how many people who open the app end up playing, and where the rest stop. `/analytics` is the dashboard, `analytics_events` is the table, and both are entirely self-hosted — no third-party script, no cookie banner to add.

Every event is a row in `analytics_events`: a `session_id` (random per browser tab), the device id the leaderboard already groups by, the room code where one applies, the event name, the normalised path (`/room/[code]`, never the real code), a small `props` object, language, and whether the device is mobile or desktop. Nine of those names are the funnel, in order: `app_open`, `create_open`, `room_created`, `joined`, `game_started`, `clue_sent`, `guess_locked`, `round_revealed`, `game_finished`. The rest are useful but never gate a step: `join_open`, `leaderboard_open`, `howto_open`, `lang_switched`, `bet_placed`, `round_skipped`, `host_claimed`, `timer_expired`, `click`, `pointer_heat`, `error_shown`, `session_end`.

Three of those are there for a different reason than the others. `round_skipped` and `host_claimed` are the rescue hatches from the section above, and neither is a feature anybody set out to use, so every one of them is a small report that something upstream failed. They are worth watching as ratios: `round_skipped` against `round_revealed` is how often a scale or a clue-giver defeats a table, and `host_claimed` against `room_created` is how often the person who opened the room walked away from it. Both fire on the acting device only, so unlike `round_revealed` their event and session counts agree. If either ratio climbs, the fix is upstream of the button — a better scale pool, a clearer clue screen, fewer host-only controls — which is exactly why they get a table on the dashboard rather than living only in Mixpanel.

`timer_expired` is the third, and it measures the same thing from the other side: how often a table cannot finish a phase under its own steam. `props.phase` is the whole value of it — `clue` says the clue screen is too hard or the limit too tight, `guess` says people are not noticing that it is their turn. The one caveat is the denominator. It can only fire in a room that chose a clock, so dividing it by all revealed rounds mixes two populations and understates it; the honest read is against revealed rounds in timed rooms only, which needs the room's settings and is therefore a question for the Supabase editor rather than the dashboard tile. Like the other two it fires once, on whichever device won the expiry race, so its event and session counts agree.

Conversion is the share of step 1 that reached a step. Drop-off is the share of the previous step that never arrived, which is the column that tells you where to look. The drop-out rate is the one headline number: sessions that opened the app and never locked a guess. Median session length comes from `session_end`, which fires with the seconds spent on the page.

Clicks are labelled rather than guessed. Every control worth counting carries a `data-ev` attribute, one delegated capture-phase listener reads the nearest one, and anything clickable without a label is counted as `(unlabelled)` — which is how a missing label gets noticed instead of silently disappearing. Mouse movement is deliberately *not* recorded as a trail: a raw `mousemove` stream is roughly sixty events a second, about thirty-six thousand rows for a ten-minute player, and it is the one signal here that would genuinely identify somebody. Instead the client keeps a 12×8 grid, samples the pointer twice a second, and sends one `pointer_heat` event per page view with the cell counts. It is off unless `NEXT_PUBLIC_TRACK_POINTER=1` is set.

The client side is a queue, not a request per event: `src/lib/client/track.ts` batches for four seconds or thirty events, posts to `POST /api/events`, and flushes through `navigator.sendBeacon` when the page goes away. The endpoint always answers 204 — `sendBeacon` has nobody to listen — and a write failure is logged and dropped, because analytics is not allowed to break a game. On the way in, the server drops any event name not on the allowlist, clamps `props` to eight shallow keys of 120 characters, and replaces a timestamp that claims to be from the future or from last week. `analytics_events` has RLS enabled and no policies, exactly like the secret tables, so nothing in a browser can read it back.

Reading it takes two routes and one page. `GET /api/analytics?period=day|week|month|all` returns the whole summary as JSON; `/analytics` renders it — the KPI tiles, the funnel with conversion and drop-off, the non-funnel events with a plain-English gloss on each, the click table, and per-room joined-versus-played. Set `ANALYTICS_TOKEN` and the API requires it as an `x-analytics-key` header, which the page forwards from `?key=…` in its own URL; leave it unset and both are open, which is fine for a party game and not fine for anything else. The SQL views `v_funnel`, `v_dropoff`, `v_clicks` and `v_room_dropoff` answer the same questions in the Supabase editor for anything the page doesn't show.

### Mixpanel

Setting `MIXPANEL_TOKEN` mirrors every event to Mixpanel as well, which buys the reports that would be tedious to build here: funnels with arbitrary step ordering and conversion windows, retention, flows, and breakdowns by any property. Supabase stays the source of truth and `/analytics` keeps working either way; Mixpanel is a second reader.

The mirror runs server-side, inside `POST /api/events`, rather than through Mixpanel's browser SDK. Three reasons. The app's own instrumentation already funnels every `track()` call through that endpoint, so nothing needs re-labelling. Requests to our own origin are never dropped by an ad blocker, while a meaningful share of browsers block Mixpanel's domain outright — and analytics that are quietly wrong are worse than none. And nothing extra ships to a phone on mobile data. The cost of that choice is Session Replay, which needs the browser SDK to record the DOM; if it ever becomes worth ~30 KB and the blocked-request problem, `mixpanel-browser` can be added alongside without touching the server path.

`src/lib/server/mixpanel.ts` holds it. `toMixpanel` is a pure mapping and is the part under test: `distinct_id` is the device id, so one person is one user across games, with `session-<id>` as the fallback for a browser that cannot keep storage; `$device_id` mirrors it so Mixpanel's simplified ID merge treats the player as an anonymous device, which is what they are — there are no accounts. `$insert_id` is a hash of the event, so a re-sent batch de-duplicates instead of inflating the funnel. `ip` is pinned to `"0"` because we never collect the player's IP and letting Mixpanel resolve one from a Vercel region would invent a location for everybody. Props named `token`, `distinct_id` or `ip` are stripped, so a stale client cannot redirect events to another project.

Two details cause almost every "it's set up but nothing appears". The data region: an EU project — the URL says `eu.mixpanel.com` — must be sent to `https://api-eu.mixpanel.com`, and the US host answers `200` while discarding the data, so `MIXPANEL_HOST` defaults to the EU one here. And the token has to exist in the environment that is actually running: locally that is `.env.local`, in production it is Vercel, and environment variables are baked at build time, so adding one needs a redeploy. `npm run mixpanel:test` sends a single `mixpanel_probe` event through the real code path to check both, and `GET /api/health` reports `"mixpanel":"on"` or `"off"`.

What is deliberately not collected: no IP address, no user agent, no cursor trail, no names, no clue text, no cross-site anything. A session id is per tab and expires with it, and the device id grants no access to anything. `localStorage.setItem("cr:no-track", "1")` or a browser's Do Not Track setting turns the whole thing off for that browser.

`ANALYTICS.md` is the metrics guide: the full event and property inventory as it actually exists in the code, which reports are worth building and how each number is computed, the two caveats that make a naive reading wrong — `round_revealed` fires once per watching device, and `session_end` fires per page-hide — and which questions would need a new event before they can be answered. It also explains why the funnel has to be split in two: the host never emits `joined` and a guest never emits `room_created`, so a single funnel silently drops half the population. `MIXPANEL-REPORTS.md` is the companion: the exact configuration for each report — type, steps, conversion window, counting method, breakdown — in the order worth building them, plus what the rest of the tool can and cannot do with this data.

## The leaderboard

Four boards, each filterable by all time, 30 days, or 7 days: team accuracy per finished game, the best single rounds, per-player clue-giving and guessing stats, and the scales that teams miss by the most. They read from `game_results` and `player_round_stats`, which are written when a game finishes and are independent of the rooms, so results outlive the rooms that produced them.

### The podium and the card behind every row

The top three of whichever board is showing stand on a podium — three heights, three medals, one big number per step — and the table underneath starts at rank 4. A table is a list of equals, and the whole point of a leaderboard is that the top of it is not; the steps say which entries mattered before anybody reads a word, which is the job the first screen has. They are laid out second-first-third, the way an actual podium stands, so the eye lands on the middle. With fewer than three entries the order stays plain first-then-second, because a two-item podium arranged 2-1 leaves a hole where third place should be and looks broken rather than sparse.

Every step and every row opens the same card, and that card is where the columns each board drops to fit on a phone actually live — a player's guessing average, a round's marker and target, the names on a team. It is a sheet over the page rather than a route: the list around an entry is the context you are reading it in, and navigating away loses the board, the period and the scroll position you had chosen. Escape, the backdrop and a button all close it, focus moves in on open, and switching board or period closes it automatically, since the ranks it was describing have just been reshuffled. On the **Rounds** board the card re-uses the game's own `Gauge` to *draw* the miss rather than state it, which is the one place a number genuinely reads worse than a picture.

The four boards have four different sets of columns, so the components read a normalised `LbEntry` — rank, title, one headline number, a handful of secondary stats, and optionally a dial — instead of one podium and one card per board. The normalisers live in `src/app/leaderboard/page.tsx` rather than on the server, because half of the work is wording: the stat labels, which language the scale poles are shown in, and which row belongs to this device are all decided in the browser. The same `Podium` component also headlines the end-of-game screen, with its `onPick` omitted so the steps render as plain blocks — everything a step could open is already further down that page, and a step that looks pressable but does nothing is worse than one that does not. Opening a card emits `lb_row_open` with the board and the displayed rank, which is the one thing the rework needs measuring: whether anybody reads past the podium.

### The personal read, at the end of a game

The score is a team number by design — the whole point is that the mean of several markers beats any one of them — but the question everyone asks when a game ends is personal, and "our team got 34" does not answer it. So the winner screen carries a second table under the scoreboard: markers placed, average error, best single marker, bullseyes, and bets won over bets placed, one row per player. It is sorted by average error, so the top row is whoever was easiest to tune into, which is a nicer thing to be told than a rank by points would be. Anyone who only ever gave clues sits at the bottom marked "clues only" rather than at a misleading zero, and rounds spent giving the clue are not counted against an average.

None of this needed a schema change. Every round already stores its own `reveal_detail` — the same jsonb blob the reveal card was drawn from, with each guess, its distance, and each bet's outcome — so the table is a fold over rows the game had already written. `foldCalibration` in `src/lib/game/engine.ts` does the folding and is pure, and `GET /api/rooms/:code/summary` is its own endpoint rather than part of the room state, because every open tab refetches the state every fifteen seconds and this is read once, on arrival. It is unauthenticated for the same reason the state read is: every number in it was on everybody's screen, round by round, as it happened.

Two details are deliberate. It is scoped by `room_id`, which is also what scopes it to *this* game — play-again deletes the room's rounds, so a rematch starts from an empty fold instead of inheriting the last game's averages. And the type it parses is loose on purpose: `reveal_detail` is jsonb, so its contents are whatever some past deploy wrote there rather than what today's interface promises, and an older shape has to produce a slightly thinner card, never a crash on the payoff screen. A read that fails leaves the table out and says nothing at all.

## Layout

`src/app` holds the pages and the API route handlers, including `api/cron/cleanup`, the one route nothing in the app calls — Vercel does, on the schedule in `vercel.json`. `src/lib/game/engine.ts` is the pure rules — scoring, averaging, bet resolution, rotation, target and code generation, input sanitising, the who-has-gone-quiet predicates behind the two rescue hatches, the phase-clock arithmetic, and the calibration fold behind the winner screen's per-player table — and has no I/O, which is why it is the part under test. `src/lib/game/clue.ts` is the clue rules, pure for the same reason and shared by the input box and the server so the two cannot drift; `src/lib/game/clue-words.ts` is the word data it reads, kept separate so the lists can be edited without reading the algorithm. `src/lib/server` is the backend service layer that owns every write, including `scales.ts`, the cached database-backed pool, and the three reads the shared room state deliberately cannot answer — `getSecretTarget` and `getLiveGuesses`, which are per-viewer, and `roomSummary`, which is once-per-game. `src/lib/server/analytics.ts` is the event ingest and the report, `src/lib/server/mixpanel.ts` the Mixpanel mirror, and `src/lib/server/schema-check.ts` what lets `/api/health` name a missing table. `src/lib/client` is the sync hook, the fetch wrappers, the localStorage identity, `track.ts`, the batching event queue, and `alarm.ts`, the synthesised countdown beep; `src/components/room/PhaseTimer.tsx` is the countdown itself, and the only component that can end a phase. `src/components/leaderboard` is the podium, the drill-down sheet and the `LbEntry` shape they both read, kept out of the page because the end-of-game screen renders the same podium. `src/lib/demo/script.ts` and `src/components/demo` are the scripted tutorial behind `/how-to-play` — the step list and the player that walks it — and are the one part of the tree that talks to nothing at all. `src/lib/scales.ts` is types and pure helpers; `src/lib/scales-data.ts` is the 262-pair catalogue, keyed by stable identifiers so labels can be reworded without orphaning old stats. `src/lib/player-tag.ts` is the four-character device tag, pure and shared so the browser can hash its own id and recognise its own leaderboard row without the server ever learning which row that is. `src/lib/i18n.ts` is a flat UA/EN dictionary shared by both sides. `scripts/gen-scales-sql.ts` generates the seed. `supabase/schema.sql` is the whole database and `supabase/scales-seed.sql` its catalogue.

`tests/engine.test.ts` covers the rules with `node:test` run through `tsx`: scoring bands and their symmetry around the target, marker averaging, bet resolution including the dead-centre case, target range, room-code format and collision rate, clue-giver rotation, turn order skipping teams too small to play, the two-per-team start gate and the teams it names as blockers, goal detection, input sanitising, device-id validation, team construction limits, scale-pool filtering and exhaustion, catalogue size and per-category minimums, the completeness and seed-safety of every scale in both languages, and the language fallback for rounds stored before the Ukrainian columns existed.

The rescue predicates get their own block, for the same reason the clue rules do: a threshold that is wrong is invisible in production, and wrong in whichever direction hurts. Fire too early and every ordinary room shows a takeover notice about a host who is sitting right there; never fire and a stuck table is left looking at a dial with no button on it. So the tests pin the two-minute window once and derive every timestamp from it — a threshold change fails one assertion with a readable message instead of four opaque ones — then walk the boundary from both sides, the deliberate asymmetry that reads a missing or unparseable stamp as *present* rather than gone, a crown pointing at a player who has already left, and the difference between an empty room having no absent host and an empty room having no clue-giver at all. The calibration fold gets two: one on the arithmetic, including a marker landing exactly on the edge of the bullseye band and a player who only ever gave clues, and one that feeds it the shapes an older deploy could have left in `reveal_detail` — nulls, a missing player id, a distance stored as a string, a bets-only blob — and asserts a thinner card rather than a crash. One more closes the loop end to end, from the ingest allowlist accepting `round_skipped` and `host_claimed` through to the rows they produce on the dashboard, because that is the path that fails silently: an event nobody allowlisted is dropped without complaint and simply reads as a feature nobody uses.

Three more pin the rules that changed after the first real game. `mayControlRound` is walked through everyone who used to be able to end a round and now cannot — the host, a teammate — then through the escape hatch, and finally through the case that only branch order prevents: a clue-giver whose own id is null must not match itself on `null === null`, which would hand the round to one arbitrary player instead of to everybody. `teamBetPoints` is pinned on the bug it exists for, a split paying nothing where a majority rule paid the point regardless, and on the two edges either side of it — a team of one still agrees, and a team that never bet has nothing to be paid. `betConsensus` is pinned on what a team is told about itself before the reveal, which is deliberately never whether it is right.

The clue rules get five tests of their own, because they are the one place where being wrong is invisible in production — a rule that quietly stops firing looks exactly like players who have stopped breaking it. They pin numbers in every form they take, including the fraction and Roman-numeral code points and the two Ukrainian collisions the word lists are built around; the word cap counting meaning and not grammar; punctuation splitting words in all four spellings while an apostrophe does not; and gluing, from both directions — `solikethisword` and `дужедалековгору` are caught while `responsibility`, `characteristic`, `відповідальність` and `непередбачуваність` pass. The fifth walks every rejection reason through the dictionary in both languages and fails if any of them is missing a message or leaves a `{placeholder}` unfilled, which is the check that stops a new reason code shipping as raw English to a Ukrainian player.

Analytics is tested the same way, because the numbers a dashboard shows are worth being sure of: `buildRows` is pinned on the allowlist, the props clamp, and the timestamp guard, and `foldEvents` on the four things that are easy to get wrong — a session counted once however often it fires, conversion and drop-off against the right denominators, a drop-out rate that is null rather than zero when nothing has happened, and clicks grouped per control *and* page with a distinct-session count beside the raw total. `toMixpanel` is pinned on the identity mapping, the millisecond timestamp, the de-duplication id, and the fact that a hostile prop cannot overwrite the project token.

The leaderboard's grouping is the other thing worth testing, because it is the only place where "who is this person" is decided. `foldPlayerRows` is exported as a pure function for exactly that reason, and the tests pin down the four cases that matter: one device across several games and several names is one row, a legacy name-only row folds into the device that answers to the same name, two devices sharing a name stay two rows, and the three roles are counted and ranked separately. Two more cover the labelling on top of that grouping: namesakes come back flagged `ambiguous` with different tags while a unique name does not, and the tag itself is stable per device, is not a prefix of the device id it came from, and stays collision-free enough to be useful — 500 synthetic devices produce more than 480 distinct tags.
